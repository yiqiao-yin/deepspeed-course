# 06 — Online Preference Optimization (Online DPO, Nash-MD, XPO)

[`../05_huggingface_dpo/`](../05_huggingface_dpo/) learns from a **fixed**
dataset collected before training started.
[`../06_huggingface_grpo/`](../06_huggingface_grpo/) samples fresh rollouts and
scores them with a **verifier**.

This folder is the gap between them: you want fresh on-policy samples, but you
have no verifier — only a judge that can say which of two responses is better.

**Book page:** [Online Preference Methods](https://yiqiao-yin.github.io/deepspeed-course/docs/tutorials/huggingface/online-preference-methods)

## Why offline DPO plateaus

Your preference pairs were generated by *some* model — an earlier checkpoint, a
different model, a human. As training proceeds the policy drifts away from
whatever produced that data, and within a few hundred steps it is generating
responses unlike anything in the dataset. **You now have no preference signal
for the region the policy actually occupies.**

The symptom is specific and easy to misread: DPO improves, then plateaus or
degrades, while `rewards/margins` keeps climbing. The margin is measuring
separation on stale data, so it looks healthy while the model does not improve.

## The three methods

| Method | arXiv | Date | Idea |
|---|---|---|---|
| **Online DPO** | [2402.04792](https://arxiv.org/abs/2402.04792) | Feb 2024 | Sample two from the current policy, judge, apply the DPO loss |
| **Nash-MD** | [2312.00886](https://arxiv.org/abs/2312.00886) | Dec 2023 | Keep the *preference model*; find its Nash equilibrium |
| **XPO** | [2405.21046](https://arxiv.org/abs/2405.21046) | May 2024 | Online DPO + a principled exploration bonus |

**Nash-MD** matters when preferences are intransitive — A beats B beats C beats
A — which a single scalar reward cannot represent by construction.

**XPO** addresses a real and under-discussed limit: online sampling can only
learn about responses the policy is *already* somewhat likely to produce. If a
better mode sits at near-zero probability, sampling will never find it.

```bash
uv run train_online_dpo.py --list-methods     # needs no GPU
```

## What plays the judge

| Judge | Cost | Notes |
|---|---|---|
| A reward model | cheap | Build one with [`../05_huggingface_reward_model/`](../05_huggingface_reward_model/) |
| A stronger LLM | moderate | This is RLAIF |
| A human | very high | Rarely feasible online |
| A rule / verifier | ~free | If you have one, use [GRPO](../06_huggingface_grpo/) |

## Online is not cheap

You now pay for generation on **every step** — two samples per prompt — plus
judging. That is most of GRPO's cost profile without GRPO's group baseline.

> **Reach for this when offline DPO has visibly plateaued, not by default.**

`--max-new-tokens` is the main cost knob: you generate two of these per prompt
per step.

## Environment & Local Testing

### Setup with `uv`

This folder is a **self-contained `uv` project** — it ships a
`pyproject.toml` and a committed `uv.lock`, so after cloning:

```bash
cd 06_huggingface_online_dpo
uv sync                    # creates .venv, installs the LOCKED versions
uv run deepspeed --num_gpus=2 train_online_dpo.py
```

`uv run` uses the project environment directly, so there is no
`activate` step. `uv sync --extra tracking` adds Weights & Biases,
which stays optional.

The lock is the point: everyone who clones resolves to identical
versions, instead of whatever `uv pip install` finds that day.
Regenerate deliberately with `uv lock --upgrade`.

## Hardware Requirements

| Resource | Minimum | Notes |
|---|---|---|
| VRAM | 24 GB | Policy + reference + judge + a KV cache for generation |
| GPUs | 2 | Budget like GRPO, not like offline DPO |
| Disk | 80 GB | Policy, judge, prompt dataset |

`ds_config.json` uses **ZeRO-3** here, unlike the offline folder's ZeRO-2 —
three models resident plus generation means every spare byte matters, which is
worth the 1.5× communication.

## Dataset shape

Offline DPO needs `prompt / chosen / rejected`. **Online needs only `prompt`** —
the pairs are manufactured during training. Hand it a preference dataset and the
script warns that `chosen`/`rejected` will be ignored.


### RunPod (creates the pod and shuts it down)

```bash

    --dry-run --collect --wait --terminate --yes

```

### Direct

```bash
deepspeed --num_gpus=2 train_online_dpo.py \
    --deepspeed ds_config.json \
    --method online_dpo \
    --reward-model ./reward-model
```

**These trainers moved.** `OnlineDPOTrainer`, `NashMDTrainer` and
`XPOTrainer` are under `trl.experimental.<method>` as of TRL 1.12, not
top-level — a plain `from trl import OnlineDPOConfig` raises `ImportError` on
any current install. `train_online_dpo.py` resolves either location, so you do
not have to care which TRL you have; it prints the module it actually resolved
at startup.

**`nash_md` does not train on TRL 1.12.** Its `GeometricMixtureWrapper.forward`
is decorated `@torch.inference_mode()`, and the logits it returns are what the
loss is computed from — so the first backward pass raises `Inference tensors
cannot be saved for backward` from inside a LayerNorm, naming neither Nash-MD
nor TRL. `online_dpo` and `xpo` are unaffected: they use inference mode only
around reward computation, whose outputs never need gradients. The script
detects the decorator and refuses up front with that explanation rather than
letting you meet the traceback. Verified on trl 1.12.0, 2× RTX 3090.

A judge is mandatory: pass exactly one of `--reward-model` or `--judge`. Without
one there is nothing to rank the sampled pairs, which is the entire point of
going online — the script refuses rather than failing deep inside the trainer.
